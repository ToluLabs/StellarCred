    @stellarcred/sdk

    @stellarcred/sdk

    Read-only client for StellarCred — check zero-knowledge credential proofs on Stellar from any protocol, frontend, or backend.

    Protocols call one function. No API key, no backend, no personal data handling — the only thing you trust is the on-chain ProofRegistry.

    Install

    npm install @stellarcred/sdk

    Note on NPM Publication: Official @stellarcred/sdk releases are cut via git tags (e.g. v0.1.1). In local development environments or before an upstream npm publish token is configured, you can consume the SDK directly from this repository:

    # Build the SDK inside the monorepo:
    cd frontend/packages/sdk
    pnpm install
    pnpm build

    # Link or import directly into your project:
    pnpm link ./frontend/packages/sdk

    Quick start

    import StellarCred from "@stellarcred/sdk";

    // Configure once at startup
    StellarCred.configure({
      registryId: process.env.PROOF_REGISTRY_ID,
    });

    // Check a claim — returns true/false
    const eligible = await StellarCred.hasClaim(walletAddress, "kyc");

    TypeScript example: a minimal, CI-typechecked walkthrough — typed claim reads, creating and signing a transaction, and the challenge flow — lives in examples/typescript-quickstart and is explained in docs/SDK_TYPESCRIPT_EXAMPLE.md.

    Configuration

    Call configure() once before any other call, or set environment variables — both approaches work in Node.js, Next.js, and edge runtimes.

    StellarCred.configure({
      registryId: "C...", // ProofRegistry contract ID
      rpcUrl: "https://soroban-testnet.stellar.org", // defaults to testnet
      networkPassphrase: "Test SDF Network ; September 2015",
      baseUrl: "https://stellarcred.xyz", // used by buildVerifyUrl
      requestTimeoutMs: 10000, // max time for each RPC read
    });

    Each is_verified / check_claim simulation is bounded by requestTimeoutMs, which defaults to 10 seconds. The timeout covers retries as well as the underlying RPC call, so a stalled Soroban node cannot leave hasClaim or getClaims pending indefinitely. A timed out read follows the normal failure behavior: it returns false or an empty result by default, and throws RpcError when throwOnError: true is used.

    Environment variables (auto-read at import time, no configure() needed):

    Variable Next.js alias
    STELLARCRED_REGISTRY_ID NEXT_PUBLIC_PROOF_REGISTRY_ID
    STELLARCRED_RPC_URL NEXT_PUBLIC_RPC_URL
    STELLARCRED_NETWORK_PASSPHRASE NEXT_PUBLIC_NETWORK_PASSPHRASE
    STELLARCRED_BASE_URL NEXT_PUBLIC_STELLARCRED_BASE_URL
    STELLARCRED_INDEXER_URL NEXT_PUBLIC_INDEXER_URL
    STELLARCRED_INDEXER_API_KEY (no browser alias — it is a secret)

    Setting STELLARCRED_INDEXER_URL alone changes nothing: reads still go to the chain until you pass source explicitly. See Indexer fast path.

    Retries and backoff

    Every RPC read, indexer request, webhook delivery and submitTransaction call retries transient failures (HTTP 429, 5xx, timeouts and network errors) with jittered exponential backoff. Terminal errors such as invalid input, other 4xx responses and contract panics are never retried. Jitter keeps clients that failed together from retrying together, so a congested or rate-limited RPC endpoint is not hit by the same burst again on every retry.

    StellarCred.configure({
      retries: 3, // retry ceiling per call
      baseDelayMs: 500, // smallest delay and start of the backoff curve
      maxDelayMs: 5000, // ceiling on any single delay
      maxElapsedMs: 15_000, // optional total retry budget per call (default: none)
      jitter: true, // true = "full"; or "decorrelated", "equal", "none" (false)
    });
    jitter Delay before retry n
    true / "full" random in [0, min(maxDelayMs, baseDelayMs × 2^(n-1))] (default)
    "decorrelated" random in [baseDelayMs, min(maxDelayMs, 3 × previous delay)]
    "equal" half of the exponential delay plus a random half (behaviour before #1056)
    false / "none" min(maxDelayMs, baseDelayMs × 2^(n-1))

    Full jitter is the default because its worst case equals plain exponential backoff (3.5 s for the default 3 retries), so a fail-soft read never waits longer during an outage than it used to. Decorrelated jitter never retries sooner than baseDelayMs but can wait up to about 11 s with the same settings.

    Every setting can also be passed per call through retryOptions (for example hasClaim(wallet, "kyc", { retryOptions: { retries: 1 } }) or submitTransaction(op, { retryOptions })), together with:

    • signal: an AbortSignal. Aborting cancels a pending delay at once and throws the abort reason; an attempt that fails because of the abort is never retried. withRetry also passes the signal to your operation as ({ attempt, signal }) so you can forward it to fetch.
    • onRetry({ attempt, delayMs, error, elapsedMs }): called before each retry with the exact delay. Errors thrown by the hook are ignored.

    Stopping a watchClaim (the returned function, a match, or its timeout) and unsubscribing from subscribeClaims cancel any retry still waiting, so a stopped poller sends no further requests. computeBackoffDelay is exported for callers that want the same curve in their own polling loops.

    Claim cache (optional)

    Calling hasClaim on every render sends one RPC simulation per render. Turn on the in-memory claim cache to answer repeated reads locally:

    StellarCred.configure({
      claimCache: true, // off by default
      claimCacheTtlMs: 30_000, // default 30s
      claimCacheMaxEntries: 1000, // default; oldest entries are evicted first
    });

    await StellarCred.hasClaim(wallet, "kyc"); // RPC
    await StellarCred.hasClaim(wallet, "kyc"); // served from memory for 30s

    // After a submission you know about, drop the stale answer:
    StellarCred.invalidate(wallet, "kyc"); // or invalidate(wallet) for every type
    • Entries are keyed by wallet, credential type, minThreshold, the trustedIssuers set and source, so different questions never share an answer. hasClaim, hasClaims, getClaim and verifyPreset share the cache; getClaims, getClaimRecord and checkClaimStatus always read the source.
    • Only successful reads are cached. A fail-soft false caused by an RPC error, a timeout or missing configuration is not, so a transient outage cannot pin a wallet to false for the TTL.
    • A cached valid answer never outlives the credential's on-chain expiry.
    • Pass fresh: true to skip the cache for one read (the result still refreshes it). watchClaim polls and the refetch of useStellarCred and createClaimGate always read fresh.
    • configure() empties the cache; clearClaimCache() does so explicitly. A read already in flight when you call invalidate is not stored.
    • The cache lives in the current process (or browser tab). It is per-instance, not shared between servers.

    Telemetry (opt-in, zero-PII)

    Diagnostic telemetry is off until you explicitly turn it on. Nothing is recorded, buffered, or sent before the first configureTelemetry({ enabled: true, … }) call.

    import { configureTelemetry, flushTelemetry, trackEvent, withTelemetry } from "@stellarcred/sdk";

    configureTelemetry({
      enabled: true, // required: explicit opt-in
      endpoint: "https://telemetry.example.com/v1/events", // or supply a `sink`
      appId: "my-app", // optional, non-identifying
    });

    // Record a sanitized event
    trackEvent("claim.check", { source: "chain", outcome: "success" });

    // Or time an operation — only name, duration and outcome are reported
    await withTelemetry("claim.read", () => StellarCred.hasClaim(wallet, "kyc"));

    await flushTelemetry(); // optional: called on batch size and on an interval

    Every event is sanitized before it can leave the process:

    • Secrets are scrubbed. Stellar G…/C…/S… keys, 64- and 128-character hex keys (including 0x…), JWTs, e-mail addresses, Bearer tokens and provider API keys are replaced with [redacted].
    • Sensitive attributes are dropped. Keys describing private keys, seeds, mnemonics, passwords, API keys, tokens, signatures, credentials, claims, proofs, witnesses, nullifiers, wallets, addresses, accounts, holders and identity fields are removed entirely, at any nesting depth.
    • Names are normalised to [a-z0-9_.-], so an address pasted into an event name cannot survive.
    • Transport is tightened. Endpoints must be https:// (loopback http:// only with allowInsecureLocalhost: true), and URLs with credentials, query strings or fragments are rejected. Requests are sent with credentials: "omit", referrerPolicy: "no-referrer" and cache: "no-store".
    • Failures never break the host. Sink and network errors are swallowed; only invalid explicit configuration throws TelemetryConfigError.

    Provide your own pipeline with sink instead of an endpoint:

    configureTelemetry({ enabled: true, sink: (events) => myCollector.send(events) });

    disableTelemetry(); // stop and discard buffered events at any time
    resetTelemetry(); // restore the initial disabled state

    The full options interface is TelemetryOptions; the sanitizers (sanitizeTelemetryAttributes, sanitizeTelemetryValue, isSensitiveTelemetryKey) are exported so integrators can apply the same filter to their own diagnostics.

    Bootstrapping from a deployment (capability descriptor)

    Instead of supplying contract IDs one by one, the SDK can configure itself from a deployment's machine-readable capability descriptor (issue #639) — you supply a single URL and the descriptor provides the network passphrase, RPC URL, and ProofRegistry contract ID:

    // One-URL setup: fetch {base}/api/capabilities and apply it.
    await StellarCred.bootstrap({ descriptorUrl: "https://app.example.com/api/capabilities" });

    // ...or rely on the configured/default baseUrl:
    await StellarCred.bootstrap(); // fetches {baseUrl}/api/capabilities

    const ok = await StellarCred.hasClaim(wallet, "kyc");

    bootstrap() throws ConfigError when the descriptor is unreachable, malformed, or has no proof_registry contract ID. The descriptor is public and cacheable — nothing sensitive — and also reports the credential types the deployment supports, a registered-issuer summary, the public indexer URL (when configured), whether sponsored submission is available, and the SDK version range known to work. Helpers fetchCapabilities() and validateCapabilitiesDescriptor() are exported for integrators that want the raw descriptor without reconfiguring.

    API

    hasClaim(wallet, claimType, opts?)

    Returns true if wallet has a currently valid, unexpired proof of claimType.

    For parameterised claims (age, income, funds), pass minThreshold to enforce the threshold on-chain. A proof generated with threshold=200,000 satisfies minThreshold: 50000 — the check is stored >= required.

    // Binary claims — no threshold needed
    const kycOk = await StellarCred.hasClaim(wallet, "kyc");
    const jurisOk = await StellarCred.hasClaim(wallet, "jurisdiction");

    // Threshold claims — enforced on-chain, fully trustless
    const ageOk = await StellarCred.hasClaim(wallet, "age", { minThreshold: 21 });
    const incOk = await StellarCred.hasClaim(wallet, "income", { minThreshold: 200000 });
    const fundsOk = await StellarCred.hasClaim(wallet, "funds", { minThreshold: 50000 });

    Pass trustedIssuers to restrict which issuer(s) a proof must come from — e.g. accept kyc only from Persona or Jumio, not a self-attested issuer. This is enforced on-chain by ProofRegistry; omit it (or leave it undefined) to accept a proof from any registered issuer, matching current behaviour. An empty array rejects every issuer.

    const kycOk = await StellarCred.hasClaim(wallet, "kyc", {
      trustedIssuers: ["G...PERSONA_ISSUER", "G...JUMIO_ISSUER"],
      requestTimeoutMs: 5000,
    });

    // Combine with a threshold — both must hold
    const incomeOk = await StellarCred.hasClaim(wallet, "income", {
      minThreshold: 100000,
      trustedIssuers: ["G...PLAID_ISSUER"],
    });

    getClaim(wallet, claimType, opts?)

    Returns the full claim record with verifiedAt and expiry timestamps, or null if the wallet has no current proof of that type. Respects trustedIssuers.

    const claim = await StellarCred.getClaim(wallet, "kyc");
    if (claim) {
      console.log(claim); // { valid: true, verifiedAt: 1719000000, expiry: 1726776000 }
    }

    // Restrict to a trusted issuer
    const trustedClaim = await StellarCred.getClaim(wallet, "kyc", {
      trustedIssuers: ["G...PERSONA_ISSUER"],
    });

    getClaimRecord(wallet, claimType, opts?)

    Fetches the low-level on-chain ProofRecord containing verifiedAt, expiry, threshold, revoked, issuer, and vkVersion, or null if no record exists.

    const record = await StellarCred.getClaimRecord(wallet, "age");
    if (record) {
      console.log(record.revoked); // false
      console.log(record.expiry); // 1780000000n
      console.log(record.threshold); // 21n
      console.log(record.issuer); // "G..."
    }

    checkClaimStatus(wallet, claimType, opts?) / getClaimOutcome(wallet, claimType, opts?)

    Performs diagnostic analysis of a credential claim, returning the granular failure or success state. Unlike boolean helpers (hasClaim), checkClaimStatus and getClaimOutcome cleanly distinguish between absent credentials (not_verified) and infrastructure failures (unavailable), preventing network/RPC errors from being conflated with rejection (#1007).

    Possible statuses:

    • "verified": Active, unrevoked, unexpired credential satisfying threshold and issuer requirements
    • "not_verified": Checked on-chain / source successfully, but no proof record was found
    • "expired": Record found, but its expiry timestamp is in the past
    • "revoked": Record found, but the issuer or admin marked it revoked
    • "unmet_threshold": Record found, but the proved threshold is below minThreshold
    • "wrong_issuer": Record found, but issued by an entity outside trustedIssuers
    • "unsupported": The requested claim type is not recognized by the protocol
    • "unavailable": RPC node, contract, transport, or network failure prevented verification
    const result = await StellarCred.checkClaimStatus(wallet, "age", { minThreshold: 21 });
    switch (result.status) {
      case "verified":
        console.log("Verified! Expires:", result.record?.expiry);
        break;
      case "expired":
        console.warn("Credential has expired. Please re-prove at StellarCred.");
        break;
      case "revoked":
        console.error("Credential was revoked.");
        break;
      case "unmet_threshold":
        console.warn("Proved threshold below requirement:", result.record?.threshold);
        break;
      case "wrong_issuer":
        console.warn("Issuer not in trusted list:", result.record?.issuer);
        break;
      case "not_verified":
        console.info("No record found. Please verify at StellarCred.");
        break;
      case "unsupported":
        console.warn("Unsupported credential type requested.");
        break;
      case "unavailable":
        console.error("RPC or network is currently unavailable:", result.error);
        break;
    }

    Typed errors (throwOnError)

    By default hasClaim / getClaims are fail-soft: a missing registryId or an RPC/simulation failure returns false / [], which is indistinguishable from "not verified." Pass { throwOnError: true } to surface a typed error instead:

    Failure Error class
    Missing registryId ConfigError
    Network / simulation failure RpcError
    Holder not verified still returns false (not an error) 
    import StellarCred, { ConfigError, RpcError } from "@stellarcred/sdk";

    try {
      const ok = await StellarCred.hasClaim(wallet, "kyc", { throwOnError: true });
      // ok === false means "not verified"; ok === true means verified
    } catch (err) {
      if (err instanceof ConfigError) {
        // SDK misconfigured — fix registryId
      } else if (err instanceof RpcError) {
        // Couldn't reach the chain — retry / degrade UI
      } else {
        throw err;
      }
    }

    TimeoutError remains the rejection used by watchClaim when its poll window expires.

    getClaims(wallet)

    Returns all active claims a wallet has proved, across all known credential types.

    const claims = await StellarCred.getClaims(wallet);
    // {
    //   kyc:          { verified: true,  expiry: 1780000000 },
    //   age:          { verified: true,  threshold: 21, expiry: 1780000000 },
    //   income:       { verified: false },
    //   jurisdiction: { verified: true,  expiry: 1780000000 },
    //   funds:        { verified: false },
    // }

    watchClaim(wallet, claimType, opts?)

    A polling helper that checks hasClaim on an interval. It either resolves a Promise or fires a callback when the claim is verified. Works with minThreshold for parameterised claims.

    Promise form — resolves true when verified, or rejects with TimeoutError after a timeout:

    try {
      await StellarCred.watchClaim(wallet, "kyc", {
        pollMs: 3000,
        timeoutMs: 120_000,
      });
      console.log("Verified!");
    } catch (err) {
      console.error("Timeout waiting for verification");
    }

    Callback form — fires onChange whenever the status changes. Returns a stop() function to cancel polling:

    const stop = StellarCred.watchClaim(wallet, "funds", {
      minThreshold: 50000,
      pollMs: 3000,
      timeoutMs: 120_000,
      onChange: (verified) => console.log("verified:", verified),
    });

    // Cancel polling manually (e.g. on component unmount)
    // stop();

    subscribeClaims(options) — real-time subscriptions (#392)

    A push-style subscription helper for protocol backends: watch a set of wallets across a set of claim types with a single subscription and receive gained / lost change events, instead of running one watchClaim poll per wallet against the chain.

    It consumes the indexer HTTP API (services/indexer) rather than ProofRegistry RPC:

    Indexer endpoint Used for Cadence
    GET /recent?limit=100[&cursor=…] the cursor-ordered verified-claims feed — every row newer than the previous (ledger_sequence, id) cursor is a potential gained for a watched wallet every pollMs (default 10 s)
    GET /claims?wallet=G… authoritative per-wallet snapshots (revoked flag + expiry) — detects lost (revoked) and reconciles state after downtime or reorg rollback every resyncMs (default 60 s)

    Expiry losses need no request at all: the indexer stores each proof's expiry timestamp, so a claim that lapses is reported as lost within one pollMs window. Event topic semantics match the on-chain proof_reg.submitted / proof_reg.revoked events documented in docs/EVENTS.md; the subscription is eventually consistent with the indexer's configured FINALITY_LAG (≈30 s on defaults).

    import { subscribeClaims } from "@stellarcred/sdk/server";

    const stop = subscribeClaims({
      wallets: ["GABC…", "GDEF…"], // any number of wallets
      claims: ["kyc", "accreditation"], // defaults to all known claim types
      // baseUrl: "https://indexer.yourdomain.xyz", // or configure({ indexerUrl }) / STELLARCRED_INDEXER_URL
      pollMs: 10_000,
      onGained: (e) => grantAccess(e.wallet, e.claim),
      onLost: (e) => revokeAccess(e.wallet, e.claim, e.reason), // "revoked" | "expired"
      onError: (err) => logger.warn(err),
    });

    // later — stop feeding events
    stop();

    Registering a webhook instead of (or in addition to) in-process callbacks lets a worker fleet receive the push:

    subscribeClaims({
      wallets: watchedWallets,
      webhook: {
        url: "https://api.yourprotocol.xyz/hooks/stellarcred",
        secret: process.env.STELLARCRED_WEBHOOK_SECRET, // sent as X-StellarCred-Webhook-Secret
      },
    });

    Each change is POSTed as JSON with headers X-StellarCred-Event: claim_gained | claim_lost and, when a secret is configured, X-StellarCred-Webhook-Secret — your receiver should reject requests that don't match it. Deliveries retry on non-2xx up to webhook.retries times and report exhaustion through onError. Payload shape:

    {
      "event": "claim_gained",
      "kind": "gained",
      "wallet": "GABC…",
      "claim": "kyc",
      "reason": null,
      "at": 1700000000,
      "issuer": "GISS…",
      "verifiedAt": 1699999000,
      "expiry": 1700604800,
      "ledgerSequence": 54321,
      "threshold": null
    }

    Options: wallets (required, validated as Stellar Ed25519 keys), claims, baseUrl (indexer origin; falls back to configure({ indexerUrl }) / STELLARCRED_INDEXER_URL / the SDK baseUrl), apiKey (sent as Authorization: Bearer for indexers running with API_KEY set), pollMs, resyncMs, emitInitialState (also replay currently-active claims as gained), requestTimeoutMs, onChange / onGained / onLost / onError, webhook.

    Notes:

    • Sizing: each poll is one /recent call regardless of watch-list size; each resync is one /claims call per wallet. Keep resyncMs within your indexer's per-IP rate limit (RATE_LIMIT_MAX, default 120 req/60 s), or raise it there for large watch lists.
    • Holder self-revocation (revoke_proof) emits no contract event, so it surfaces as lost (expired) when the indexed proof expires; issuer revocations surface as lost (revoked) on the next resync.
    • Prefer @stellarcred/sdk/server — subscriptions belong in a backend process, and browser bundles cannot guard webhook secrets.

    buildVerifyUrl(options)

    Builds a StellarCred verification URL to redirect users to. BuildVerifyUrlOptions and BuildVerifyUrlClaimParams are exported from the package. After verifying, StellarCred returns the user to returnUrl with ?sc_verified=true&sc_wallet=<address>&sc_claims=<claim-types> appended. sc_claims is a comma-separated list of the claim types issued in the current session (not all-time claims), allowing protocols to optimistically update their UI before an on-chain read completes.

    import { buildVerifyUrl, type BuildVerifyUrlOptions } from "@stellarcred/sdk";

    const options = {
      returnUrl: "https://yourapp.xyz/markets",
      claim: "age",
      claimParams: { threshold_years: "21" },
      expiresInMinutes: 15,
    } satisfies BuildVerifyUrlOptions;

    const url = buildVerifyUrl(options);

    Builds a strongly typed StellarCred verification URL to redirect users to. After verifying, StellarCred returns the user to returnUrl with ?sc_verified=true&sc_wallet=<address>&sc_claims=<claim-types> appended. sc_claims is a comma-separated list of the claim types issued in the current session (not all-time claims), allowing protocols to optimistically update their UI before an on-chain read completes.

    import {
      buildVerifyUrl,
      type BuildVerifyUrlOptions,
      type AgeVerifyUrlOptions,
      type ThresholdVerifyUrlOptions,
      type JurisdictionVerifyUrlOptions,
    } from "@stellarcred/sdk";

    // 1. Basic — redirect to verify KYC (absolute or relative returnUrl)
    const kycUrl = buildVerifyUrl({
      returnUrl: "https://yourapp.xyz/deposit",
      claim: "kyc",
    });

    // Relative returnUrl is also supported
    const localUrl = buildVerifyUrl({
      returnUrl: "/dashboard",
      claim: "kyc",
    });

    // 2. Financial claims with threshold — number or string accepted
    const fundsUrl = buildVerifyUrl({
      returnUrl: "https://yourapp.xyz/vault",
      claim: "funds",
      claimParams: { threshold: 50_000 }, // proves balance >= $50,000
    } satisfies ThresholdVerifyUrlOptions);

    // 3. Age gate — minimum age in years (number or string)
    const ageUrl = buildVerifyUrl({
      returnUrl: "https://yourapp.xyz/markets",
      claim: "age",
      claimParams: { threshold_years: 21 }, // require 21+
    } satisfies AgeVerifyUrlOptions);

    // 4. Jurisdiction — block specific countries (array or comma-separated string)
    const geoUrl = buildVerifyUrl({
      returnUrl: "https://yourapp.xyz/app",
      claim: "jurisdiction",
      claimParams: { restricted: ["840", "364"] }, // ISO 3166-1 numeric codes
    } satisfies JurisdictionVerifyUrlOptions);

    // 5. Multi-claim verification request
    const multiUrl = buildVerifyUrl({
      returnUrl: "https://yourapp.xyz/onboarding",
      claims: ["kyc", "funds"],
      claimParams: { threshold: "10000" },
    });

    // 6. Security options: expiry, single-use token (jti), and CSRF state
    const secureUrl = buildVerifyUrl({
      returnUrl: "https://yourapp.xyz/callback",
      claim: "kyc",
      wallet: "GA7QYNF7SOWQ3GLR2BGMZEHXAVIRZA4KVWLTJJFC7MGXUA74P7UJVWGS",
      state: "opaque_csrf_session_id",
      expiresInMinutes: 15, // link expires in 15 minutes
      singleUse: true, // embeds unique jti consumed on first visit
      trustedIssuers: ["GCFXHS4GMXBYRBAPOH2KZIGNDQBMV5DNZD5WT6VHGQ3M7N2TRB664BXO"],
    });

    ⚠️ Security Notice (Issue #543): Query parameters in the return URL (sc_verified, sc_wallet) are untrusted hints. Never grant access solely based on sc_verified=true or sc_wallet. Always require the holder to sign a challenge via verifyWalletClaim to prove key control and confirm on-chain credentials.

    Validating credential JSON

    Use the validator whenever credential JSON crosses a trust boundary — a user pasting an exported credential, a QR scan, an import file, or a request body from another service. It rejects malformed shapes before they reach storage or a verification flow, and reports every problem at once with the offending field path.

    import { parseCredentialJson } from "@stellarcred/sdk";

    const result = parseCredentialJson(pastedJson);
    if (!result.valid) {
      // e.g. "issuerId — must be a non-empty string."
      return { errors: result.errors };
    }

    // result.credential is typed as CredentialJson.
    await storeLocally(result.credential);

    If you already have an object (for example await req.json()), call validateCredential(value) instead. Server handlers that prefer exceptions can use assertValidCredential(value), which throws a CredentialValidationError carrying the same issues list.

    The helper only checks shape and required metadata (type, issuerId, holder, value, salt, commitment, signature/public-key byte arrays, and expiry). It does not prove the credential on-chain or verify that the commitment is valid — for that, keep using hasClaim / checkClaimStatus, which read from ProofRegistry.

    Offline / air-gapped verification

    Air-gapped devices — border-control desks, venue-entry terminals, kiosks on a locked-down network — cannot reach a Soroban RPC endpoint. createOfflineVerifier verifies a zero-knowledge presentation using only material already on the device: cached verifier keys, a cached state snapshot, and a local UltraHonk verifier. The module performs no I/O at all; there is no fetch, no RPC client, and no fallback to the network.

    import { readFileSync } from "node:fs";
    import { createOfflineVerifier } from "@stellarcred/sdk";

    const verifier = createOfflineVerifier({
      verifierKeys: JSON.parse(readFileSync("cache/vks.json", "utf8")),
      stateSnapshot: JSON.parse(readFileSync("cache/state.json", "utf8")),
      trustedIssuers: ["GBBB…"],
      maxSnapshotAgeSeconds: 86_400, // default: 24 hours
    });

    const result = await verifier.verify({
      credential_type: "age",
      holder: "GAAA…",
      proof: "0x…", // UltraHonk proof bytes, hex
      public_inputs: "0x…", // concatenated 32-byte field elements, hex
      vk_version: 1,
      issuer_id: "GBBB…",
      issuer_pub_key: "0x…", // 64 bytes: x || y
      commitment: "0x…",
      min_threshold: 18,
    });

    if (!result.valid) console.error(result.code, result.message);

    Verification is fail-closed and checks, in order: presentation shape and proof length; snapshot freshness and network; the cached verifier key (exact VK version, deprecation); the cached claim record (presence, VK version, revocation, expiry); commitment binding to the record, revocation list and public inputs; issuer trust and issuer-key binding; Merkle root; thresholds; nullifier replay; and finally the UltraHonk proof itself. Every failure carries a stable code (e.g. stale_state_snapshot, revoked, issuer_key_mismatch, proof_invalid) and a checks trace, so a terminal can log exactly where verification stopped.

    Cache format. The snapshot reuses the indexer's /claims wire shape for claim rows (wallet, credential_type, verified_at, expiry, issuer, revoked, threshold, ledger_sequence), so an exporter can persist GET /claims output verbatim and add the top-level metadata (snapshotVersion: 1, capturedAt, ledgerSequence) plus optional nullifiers, issuerKeys, revokedCommitments and merkleRoot. Rows may also carry commitment, issuer_pub_key and vk_version when the exporter has them.

    Proof backend. The built-in backend loads the optional @aztec/bb.js package from the device and verifies against the circuit bytecode cached on the verifier key (circuit_bytecode), since bb.js derives the verification key from the circuit artifact. It verifies single-threaded, so the device needs no SharedArrayBuffer or cross-origin isolation. A device that vendors bb.js elsewhere, or uses a native verifier, can pass its own proofVerifier instead:

    const verifier = createOfflineVerifier({
      verifierKeys,
      stateSnapshot,
      proofVerifier: async ({ verifierKey, proof, publicInputs }) =>
        nativeUltraHonkVerify(verifierKey, proof, publicInputs),
    });

    public_inputs is the prover's field list exactly as bb.js emits it: Noir flattens a [u8; N] public input into N single-byte fields, so pass the output through unchanged. The verifier binds a 64-byte issuer key in either the packed or the byte-expanded encoding.

    When the backend is unavailable the result is proof_backend_missing — never a silent valid: true. A stale snapshot is likewise a hard failure rather than a warning; refresh it on a networked device and carry the new file across.

    Full integration example

    import StellarCred from "@stellarcred/sdk";

    StellarCred.configure({ registryId: process.env.PROOF_REGISTRY_ID });

    async function handleDeposit(wallet: string) {
      // Check all required claims
      const [kycOk, fundsOk] = await Promise.all([
        StellarCred.hasClaim(wallet, "kyc"),
        StellarCred.hasClaim(wallet, "funds", { minThreshold: 50000 }),

      if (!kycOk || !fundsOk) {

        return redirect(

            claim: missing,
            ...opts,
          }),
        );
      }

      // All claims verified — proceed
      processDeposit(wallet);
    }

    Trust boundary

    The SDK is designed to work in both browsers and Node.js, but there is an important boundary between public client-side config and private server-side config. Understanding this boundary prevents accidental secret leakage.

    What is safe to expose to the client

    Config Safe for browser? Why
    registryId (ProofRegistry contract ID) ✅ Yes A public Stellar contract address — no secret
    rpcUrl ✅ Yes A public RPC endpoint — no secret
    networkPassphrase ✅ Yes A well-known network identifier — no secret
    baseUrl ✅ Yes The StellarCred public URL — no secret

    Pass these via NEXT_PUBLIC_* (Next.js) or VITE_* (Vite) env vars so they are available in browser bundles:

    # .env.local (Next.js)
    NEXT_PUBLIC_PROOF_REGISTRY_ID=C...
    NEXT_PUBLIC_RPC_URL=https://soroban-testnet.stellar.org

    What must stay server-side only

    Config / Package Server-only? Why
    ISSUER_PRIVATE_KEY ✅ Server-only Signs credentials — exposure lets anyone forge credentials
    @stellarcred/issuer ✅ Server-only Contains the signing key; throws if imported in a browser
    Server-side hasClaim checks ✅ Server-only for access control Client-side checks are optimistic UI only (see below)

    Never use NEXT_PUBLIC_ on ISSUER_PRIVATE_KEY or any other secret.

    Server-side re-verification is required

    Client-side claim checks (via hasClaim in the browser, useStellarCred, etc.) are optimistic UI only — they improve UX by providing immediate feedback but they cannot be trusted for access control:

    • The browser environment is not trusted; results can be spoofed by the user.
    • sc_verified=true return-URL params are untrusted URL hints, not proofs.

    Always re-verify claims server-side before granting access, using the wallet address the user has actually authenticated with (not one from a URL param):

    // ✅ Server-side gate (API route, middleware, server component)
    import StellarCred from "@stellarcred/sdk/server";

    const ok = await StellarCred.hasClaim(authenticatedWallet, "kyc");
    if (!ok) return res.status(403).json({ error: "KYC required" });

    // ⚠️  Client-side check — optimistic UI only, not a security gate
    import StellarCred from "@stellarcred/sdk";

    const ok = await StellarCred.hasClaim(wallet, "kyc");
    if (!ok) router.push("/verify"); // redirect to verify, but server will also check

    Server entry point: @stellarcred/sdk/server

    When importing the SDK in server-side code (API routes, middleware, server components, Lambda handlers, etc.), use the dedicated server entry point:

    // ✅ Explicit server-side import
    import StellarCred from "@stellarcred/sdk/server";
    import { hasClaim, configure } from "@stellarcred/sdk/server";

    This is a thin re-export of the same SDK — the API is identical. The separate path makes the intent explicit at the import site and suppresses the development-mode warning described below.

    Server-side presentation tokens (#1062)

    Next.js App Router Server Components cannot access browser wallet extensions, so a page rendered on the server cannot sign a challenge or read a wallet itself. Presentation tokens solve that without a custom verification API route: the holder's browser packages the credentials it wants to present into a compact token signed by its Stellar wallet, and the Server Component verifies that token directly.

    Token format

    scpt1.<base64url(payload JSON)>.<base64url(Ed25519 signature)>

    The signature is made by payload.wallet over the domain-separated message stellarcred/presentation-token/v1 + "\n" + the encoded payload. Tokens are short-lived (five minutes by default), can bind an audience, and carry an optional nonce for callers that need single-use bookkeeping.

    Create a token (holder's browser)

    import { createPresentationToken } from "@stellarcred/sdk";

    const token = await createPresentationToken({
      wallet: publicKey,
      claims: ["kyc", "age"],
      audience: "app.example.com",
      sign: async (message) => {
        // Freighter and other Stellar wallets sign arbitrary UTF-8 messages.
        const { signedMessage } = await freighter.signMessage(message);
        return signedMessage; // hex, base64, or Uint8Array are all accepted
      },
    });

    await fetch("/api/session", {
      method: "POST",
      headers: { "content-type": "application/json" },
      body: JSON.stringify({ token }),
    });

    Verify in a Server Component (Node.js or Edge runtime)

    // app/dashboard/page.tsx
    import { cookies } from "next/headers";
    import { verifyPresentationToken } from "@stellarcred/sdk/server";

    export default async function Dashboard() {
      const token = (await cookies()).get("sc_presentation")?.value ?? "";

      const result = await verifyPresentationToken(token, {
        requiredClaims: ["kyc"],
        audience: "app.example.com",
      });

      if (!result.ok) {
        // result.failureReason is machine-readable, result.error is human-readable.
        return <p>Access denied: {result.error}</p>;
      }

      return <p>Welcome, KYC-verified {result.wallet}</p>;
    }

    Verify in an API route, middleware, or Server Action

    The same helper works anywhere server-side, with no browser globals:

    // app/api/gate/route.ts
    import { verifyPresentationToken } from "@stellarcred/sdk/server";

    export async function POST(request: Request) {
      const { token } = (await request.json()) as { token?: string };

      const result = await verifyPresentationToken(token ?? "", {
        requiredClaims: ["kyc"],
        audience: new URL(request.url).host,
        claimOptions: { trustedIssuers: [TRUSTED_PERSONA_ISSUER] },
      });

      if (!result.ok) {
        return Response.json({ error: result.error }, { status: 401 });
      }

      return Response.json({ wallet: result.wallet, claims: result.claims });
    }

    What verification checks

    1. Envelope and payload shape — prefix, segments, version, wallet, claims, timestamps, audience, and nonce types.
    2. Signature — Ed25519 over the signed payload, using the same verifyWalletSignature implementation as the wallet-challenge flow.
    3. Freshness — issuedAt is not in the future and expiresAt has not passed (60 seconds of clock skew by default; set clockSkewSeconds).
    4. Expectations — requiredClaims, wallet, and audience when supplied.
    5. On-chain credentials — every presented claim is re-checked with hasClaim, and failures are enriched through checkClaimStatus. Set verifyClaims: false only when a signature-only check is genuinely intended.

    verifyPresentationToken never throws for untrusted token content or remote verification failures. It returns a typed result:

      ok: boolean;
      wallet: string;

      signatureValid: boolean;
      claimsChecked: boolean;
      claimsValid?: boolean;
      claimStatuses?: Partial<Record<ClaimType, CredentialStatusResult>>;
      failedClaim?: ClaimType;
      failureReason?:
        | "malformed_token"
        | "unsupported_version"
        | "invalid_payload"
        | "invalid_wallet"
        | "invalid_signature"
        | "token_expired"
        | "token_not_yet_valid"
        | "expiry_required"
        | "audience_mismatch"
        | "wallet_mismatch"
        | "claim_missing"
        | "claim_not_verified"
        | "credential_expired"

    Security notes

    • Always pass requiredClaims and audience for access control. A valid signature only proves who signed the token, not what the caller needs.
    • Keep tokens short-lived. createPresentationToken defaults expiresAt to five minutes; verification requires it unless you opt out with requireExpiry: false.
    • For strict single-use semantics, include a nonce in the token and record it server-side before granting access. Verification does not consume it.
    • Claim checks use ProofRegistry reads by default. claimOptions.source follows the normal trust rules in §Indexer fast path — never use an indexer-only read as the sole basis for an access-control decision.
    • The helper is runtime-compatible with Node.js and Edge: it has no browser dependencies and does not access window, document, storage, wallet extensions, or Node-only built-ins.

    Development-mode boundary warning

    In development (NODE_ENV !== "production"), the SDK emits a one-time console.warn when configure() is called from a browser context with values that appear to come from server-only environment variables (e.g. STELLARCRED_REGISTRY_ID or bare PROOF_REGISTRY_ID without a NEXT_PUBLIC_ prefix). This catches the common mistake:

    // ⚠️  Wrong — uses a server-only env var name
    StellarCred.configure({ registryId: process.env.PROOF_REGISTRY_ID });

    // ✅ Right — uses the public Next.js alias
    StellarCred.configure({ registryId: process.env.NEXT_PUBLIC_PROOF_REGISTRY_ID });

    The warning only fires once per page load, only in development (when NODE_ENV is not "production"), and only in a browser context. It is silent in production, in Node.js, and when no suspicious indicators are present.

    To silence the warning permanently for server-side code, import from @stellarcred/sdk/server — the warning is only relevant for browser bundles.

    Indexer fast path (optional)

    By default every read simulates against ProofRegistry. That is the correct trust model — the only thing your protocol needs to trust is the contract — but it costs a round trip to a Soroban RPC node per credential type, and the chain cannot answer questions like "what has this issuer ever issued?" or "what happened recently?".

    A StellarCred indexer answers those faster. The SDK can read from one, off by default and only when you ask for it per call.

    ⚠️ Read this before you gate anything on it

    An indexer is an off-chain cache of public chain data, operated by someone. It can be stale, lagging, misconfigured, or dishonest. A claim read with source: "indexer" is not a proof.

    Never use source: "indexer" as the sole basis for a security decision. Gate access with source: "chain" (the default) or source: "indexer-verified". Use plain "indexer" for UI, analytics, previews, and anywhere a wrong answer costs you a flicker rather than an authorisation bypass.

    The three sources

    import StellarCred from "@stellarcred/sdk";

    StellarCred.configure({
      registryId: process.env.PROOF_REGISTRY_ID,
      indexerUrl: process.env.STELLARCRED_INDEXER_URL,
      // indexerApiKey: process.env.STELLARCRED_INDEXER_API_KEY,  // only if the indexer gates /claims
    });

    // 1. Default — trust-minimised. Use this for gating.
    const ok = await StellarCred.hasClaim(wallet, "kyc");

    // 2. Fast path — trusts the indexer operator. Not for security decisions.
    const preview = await StellarCred.hasClaim(wallet, "kyc", { source: "indexer" });

    // 3. Trust anchor — reads the indexer, then confirms on-chain and returns the
    //    CHAIN's answer. Use when you want drift detection alongside the read.
    const gated = await StellarCred.hasClaim(wallet, "kyc", {
      source: "indexer-verified",
    });

    source is accepted by hasClaim, getClaim, hasClaims, getClaims, verifyPreset, and watchClaim, and is inherited by createClaimGate and useStellarCred through the options they forward.

    "indexer-verified" is not faster than "chain". It still performs a chain read, because the chain is what makes the answer trustworthy. Its value is that a disagreement between the two is logged, which tells you your indexer has drifted before your users are affected by it:

    [StellarCred] Indexer disagreed with the chain for claim "kyc": indexer said
    true, ProofRegistry said false. The chain result was used. …

    That warning is rate-limited to once per process and — unlike the SDK's other warnings — fires in production too, because an integrity signal you only see in development is not much use.

    What the fast path does and does not change

    minThreshold and trustedIssuers are both honoured on the indexer path. The SDK re-evaluates them from the raw claim row using the same predicates the contract uses, so a call is drop-in compatible across sources:

    Contract rule Indexer equivalent
    !revoked row.revoked === 0
    expiry > ledger.timestamp() expiry > Date.now()/1000
    issuer_is_trusted(list, issuer) same, with an empty issuer treated as the contract's None and therefore rejected when a filter is set
    threshold.unwrap_or(0) >= min (row.threshold ?? 0) >= min

    Known divergences

    These are inherent to reading a cache rather than the chain, and are the reason "indexer" must not gate access:

    • Clock source. The contract compares expiry against the ledger timestamp; the SDK compares against your local wall clock. Near an expiry boundary the two can disagree, in either direction.
    • Lag. The indexer trails the chain by its finality lag plus poll interval (seconds by default, longer if it is unhealthy). A just-submitted claim can read as absent, and a just-revoked claim can still read as valid. Check the indexer's GET /health for lag and status if you depend on freshness.
    • Trust. You are trusting the indexer operator to serve you honest data. "chain" and "indexer-verified" do not ask you to.

    Fan-out and caching

    GET /claims?wallet=… returns all of a wallet's claims in one response, so a getClaims fan-out over the six credential types issues one HTTP request, not six. To do that the SDK memoises indexer rows per wallet for indexerCacheMs (default 2000, set 0 to disable).

    This cache applies only to "indexer" and "indexer-verified" reads. Chain reads are only cached when you opt in to the claim cache; otherwise every source: "chain" call is a fresh simulation.

    Failure behaviour

    The indexer path follows the SDK's existing fail-soft convention: an unreachable indexer, an HTTP error, or a malformed body yields false / null / [] rather than throwing, and throws IndexerError (or ConfigError when indexerUrl is missing) under throwOnError: true. Failed responses are not cached.

    For source: "indexer-verified" a failed indexer read is not fatal — the chain read still happens and still decides the result.

    The API key is a secret

    indexerApiKey is sent as Authorization: Bearer. There is deliberately no NEXT_PUBLIC_ alias for it, and configuring one from a browser context warns in development: shipping it to the browser hands it to every visitor. Either read from the browser without a key, or proxy indexer reads through your own backend.

    Note also that the indexer's CORS policy does not allow an X-API-Key header through a browser preflight, which is why the SDK uses Authorization.

    How it works

    StellarCred stores ZK proofs on Stellar. A holder proves a claim once (in their browser, using UltraHonk / Barretenberg); the result is cached in the ProofRegistry contract. Your protocol reads it with a single free simulation — no wallet connection, no fee, no personal data.

    The minThreshold check calls ProofRegistry.check_claim on-chain, which compares the threshold stored in the proof's public inputs against your required minimum. It is not a frontend check — the contract enforces it.

    Server-Side Wallet Challenge & Verification (verifyWalletClaim)

    ⚠️ CRITICAL SECURITY WARNING: The Wallet Spoofing Pitfall

    Do NOT use hasClaim(wallet, ...) alone to gate server-side resources or create authenticated sessions.

    Anyone can look up a verified public key on-chain and pass it in a request body, query parameter, or header. Checking hasClaim(untrustedAddress, "kyc") only proves that someone owns credentials for that address, not that the current HTTP caller controls that address!

    To securely gate access, your server must issue a cryptographic challenge, have the client sign it with their Stellar wallet (Freighter, Albedo, etc.), and verify both the signature and on-chain credential claim.

    1. Issue a Challenge (Server)

    import { createWalletChallenge } from "@stellarcred/sdk";

    // In your GET /api/auth/challenge endpoint:
    const challenge = createWalletChallenge({
      domain: "yourapp.com",
      statement: "Sign in to access accredited investor pool",
      ttlMs: 5 * 60 * 1000, // 5 minutes validity
    });

    // Send `challenge` JSON to frontend
    res.json(challenge);

    2. Sign Challenge (Client / Wallet)

    // In your frontend with Freighter or wallet of choice:
    import { signMessage } from "@stellar/freighter-api";

    const signature = await signMessage(challenge.message);
    // Send { wallet, challenge, signature } to POST /api/auth/verify

    3. Verify Wallet Control & On-Chain Claim in One Call (Server)

    import { verifyWalletClaim } from "@stellarcred/sdk";

    // In your POST /api/auth/verify endpoint:
    const result = await verifyWalletClaim({
      wallet: req.body.wallet,
      challenge: req.body.challenge,
      signature: req.body.signature,
      claim: "kyc",
      // Optional threshold or issuer requirements:
      // claimOptions: { minThreshold: 50000, trustedIssuers: ["G..."] },
    });

    if (!result.ok) {
      // Returns detailed diagnostics:
      // result.signatureValid === false (spoofing attempt or altered challenge)
      // result.claimValid === false (wallet doesn't hold the on-chain claim)
      return res.status(403).json({ error: result.error });
    }

    // ✅ Proven wallet control AND valid on-chain KYC credential!
    // Proceed with issuing session cookie or JWT:
    createSession(req, result.wallet);

      expect(result.ok).toBe(true);
    });
    • MockWalletProvider: a SEP-43 wallet (getAddress, signMessage, signTransaction, plus signChallenge) backed by a real Ed25519 keypair, so its signatures pass verifyWalletSignature / verifyWalletClaim. Pass { secret } for a fixed address, { reject: true } (or call rejectRequests()) to simulate a dismissed prompt (MockWalletRejectedError, code: -4). calls records every request.
    • CredentialFactory: create({ type, holder, claimParams, expiry, ... }) returns credential JSON in the /api/issue shape that passes validateCredential, signed with a real secp256k1 issuer key over the commitment (low-s, no pre-hash, as @stellarcred/issuer signs). Pass issuerPrivateKey, issuerId and now for deterministic output; createMany(types) issues several for one holder; verifyCredentialSignature(credential) checks a signature.
    • MockProofRegistry: an in-memory ProofRegistry with the contract's read semantics. prove(credential) stores a proof (holder, type, issuer, threshold and expiry taken from the credential); addProof({ holder, type, issuer, threshold, expiresInSeconds }) stores one directly. Then revoke(holder, type, reason), setLedgerTime(s) / advanceTime(s) for expiry, useNullifier(context, nullifier) for verifyUniquePersonhood, failNextReads(error, times) for RPC failures, reset(), and calls for assertions. installMockRegistry(registry?) routes hasClaim, getClaim, getClaims, hasClaims, checkClaimStatus, getClaimRecord, verifyPreset, verifyWalletClaim and isNullifierUsed to it without any registryId; uninstallMockRegistry() restores the real client.

    Factory credentials are not provable: the commitment is a random field element rather than the Poseidon2 hash of value and salt, so a real prover or verifier rejects them. Never ship this entry point in production code.

    Batch signature verification (worker threads)

    Verifying thousands of wallet-signed presentations one at a time blocks the Node.js event loop. BatchVerifierPool runs the Ed25519 checks on worker_threads instead and returns one result per input, in input order. It is Node.js only and exported from @stellarcred/sdk/server (not the browser entry point).

    import { BatchVerifierPool, verifyWalletSignaturesBatch } from "@stellarcred/sdk/server";

    // One-shot: starts a temporary pool and tears it down afterwards.
    const results = await verifyWalletSignaturesBatch(presentations, { concurrency: 4 });

    // Long-lived: reuse workers across batches, then close.
    const pool = new BatchVerifierPool({ chunkSize: 128, chunkTimeoutMs: 10_000 });
    const more = await pool.verify(presentations); // [{ index, wallet, valid, reason? }]
    await pool.close();

    Each presentation is { wallet, message, signature } (signature as hex, base64, or bytes). The result for an item matches verifyWalletSignature(wallet, message, signature); a failed item carries a reason: invalid_wallet, invalid_signature, worker_error, timeout, or pool_closed. Bad items never reject the batch. Options: concurrency (default: CPU cores - 1), chunkSize (default 64), chunkTimeoutMs (default 30 000; a stuck worker is replaced). This checks signatures only — it does not read on-chain claims; use hasClaim for that.

    Release Process

    The SDK follows Semantic Versioning. Releases are fully automated through .github/workflows/release.yml.

    How Releases Work:

    1. Version Declaration: The canonical version is maintained in frontend/packages/sdk/package.json (e.g. "version": "0.1.1").
    2. Cutting a Release:
      • Update package.json version and document changes in frontend/packages/sdk/CHANGELOG.md and root CHANGELOG.md.
      • Create and push a signed git tag matching the version with a v prefix:
        git tag -a v0.1.1 -m "Release v0.1.1"
        git push origin v0.1.1
    3. Workflow Execution:
      • .github/workflows/release.yml triggers on v* tag pushes.
      • It validates that the git tag version strictly matches package.json.
      • Runs pnpm build to compile the dual CJS/ESM distribution bundles with TypeScript definitions.
      • Generates release notes from conventional commit messages.
      • Creates an official GitHub Release with release artifacts.
      • Publishes @stellarcred/sdk with public access to the npm registry using NPM_TOKEN.

    Credential version compatibility

    StellarCred stamps every issued credential with the deployment and circuit version it was issued against. When a ZK circuit is upgraded, the verifying key changes — a proof generated by the old circuit cannot be verified on-chain. The version helpers let you detect stale credentials before the holder starts the proof flow.

    getDeploymentCircuitVersion(network, proofRegistryId)

    Returns the circuit version for a deployment, without needing a credential.

    import { getDeploymentCircuitVersion } from "@stellarcred/sdk";

    const current = getDeploymentCircuitVersion("testnet", process.env.NEXT_PUBLIC_PROOF_REGISTRY_ID);
    // "1.0.0-beta.9+0.87.0"  or  null (unrecognised deployment)

    getCredentialCircuitVersion(credential)

    Extracts the circuit version that was active when a credential was issued.

    import { getCredentialCircuitVersion } from "@stellarcred/sdk";

    const info = getCredentialCircuitVersion(credential);
    // {
    //   circuitVersion:  "1.0.0-beta.9+0.87.0",  // null for legacy credentials
    //   network:         "testnet",
    //   proofRegistryId: "C...",
    //   issuedAt:        1700000000,
    // }

    isCompatibleCredential(credential, expectedVersion)

    Returns true when a credential's circuit version matches the current deployment.

    import { isCompatibleCredential, getDeploymentCircuitVersion } from "@stellarcred/sdk";

    const current = getDeploymentCircuitVersion("testnet", registryId) ?? "";
    if (!isCompatibleCredential(credential, current)) {
      // Prompt the holder to re-verify before starting the proof flow.
      redirectToReVerify();
    }

    getCredentialVersionStatus(credential, expectedVersion)

    Returns a typed discriminant for richer UI handling:

    Status Meaning
    "compatible" Version matches — safe to prove
    "incompatible" Version differs — holder must re-verify
    "legacy" No deployment field — issued before version stamping
    "unknown" Deployment recognised but not in the version registry 
    import { StellarCred, getDeploymentCircuitVersion } from "@stellarcred/sdk";

    const current = getDeploymentCircuitVersion("testnet", registryId) ?? "";
    const status = StellarCred.getCredentialVersionStatus(credential, current);

    switch (status) {
      case "compatible":
        startProofFlow(credential);
        break;
      case "incompatible":
        showReVerifyBanner();
        break;
      case "legacy":
        showLegacyWarning();
        break;
      case "unknown":
        showUnknownDeploymentError();
        break;
    }

    Recommended protocol flow for stale credentials

    1. At app startup (or when the holder's credential is loaded), call getDeploymentCircuitVersion() once to get the current expected version.
    2. Before entering the proof flow, call getCredentialVersionStatus(credential, current).
    3. If the status is not "compatible", show a banner explaining the circuit was upgraded and offer a "Re-verify" button that links to /verify.
    4. On re-verify completion, the holder receives a fresh credential stamped with the latest circuit version — subsequent compatibility checks will pass.

    Why re-verify instead of re-prove? The ZK proof is tied to the commitment and circuit verifying key. A proof generated by an old circuit does not verify against the new key. The credential itself is also bound to the issuer's signature, so only the issuer can re-stamp it for the new circuit — the holder must go through a new issuance flow.

    Tree-Shaking & Bundle Optimization

    @stellarcred/sdk is designed for minimal bundle overhead across both browser and server applications:

    • sideEffects: false: Configured in package.json to enable full dead-code elimination in modern bundlers (Webpack, Vite, Rollup, Next.js).
    • Subpath entrypoints:
      • import StellarCred from "@stellarcred/sdk": Primary client entrypoint.
      • import StellarCred from "@stellarcred/sdk/server": Node.js and Edge backend runtimes.
    • Dynamic On-Demand Module Loading:
      • Heavy RPC modules and Soroban contract bindings (@stellar/stellar-sdk and proof-registry) are loaded on-demand via dynamic import() only when on-chain contract queries (hasClaim, getClaim) are executed.
      • Offline helpers like buildVerifyUrl(), buildBadgeUrl(), buildBadgeEmbedCode(), CLAIM_TYPES, TimeoutError, and createClaimGate() execute with zero network overhead and without loading heavy Soroban dependencies.

    Real-time events (EventStream)

    import { EventStream } from "@stellarcred/sdk";

    const stream = new EventStream({
      url: "wss://indexer.example/events",
      transport: "websocket", // or "sse" with an https:// URL
      onError: console.error,
    });

    stream.on("proof.submitted", (e) => console.log(e.holder, e.claim, e.expiry));
    stream.on("proof.revoked", (e) => console.log("revoked", e.claim));
    stream.connect();
    // later: stream.disconnect();
